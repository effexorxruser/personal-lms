# Пайплайн заявок на новые курсы

Документ описывает управляемый human-in-the-loop процесс между учеником, администратором платформы и внешними инструментами authoring (ChatGPT / Deep Research) и импорта кода (**Codex/Cursor**).

LMS personal-lms **не** выполняет автономную генерацию курса и **не** интегрируется с GitHub API для auto-commit/auto-PR/auto-merge.

## Участники и роли

- **Ученик (learner)** — создаёт заявку после входа в систему (`role=learner|admin`).
- **Администратор (`role=admin`)** — просматривает все заявки, может менять статус и заметки, копирует детерминированные промпты из LMS.
- **Внешний ChatGPT / Deep Research** — место генерации содержательного course pack по скопированному промпту.
- **Codex/Cursor вне платформы** — агент, который импортирует уже готовый pack в дерево репозитория `content/` и создаёт PR вручную.

## Последовательность шагов

1. **Ученик отправляет форму**  
   Переход: «Запросить новый курс», заполнение цели, уровня, длительности, тем и артефактов. После сохранения создаётся запись со статусом `submitted`.

2. **Администратор рассматривает заявку**  
   Список: `/admin/course-requests`; карточка заявки с полями и историей времени создания.

3. **Промпт для ChatGPT**  
   Страница админ-детали показывает текст, собираемый **детерминированно на сервере**. Администратор копирует его в свой чат или Deep Research-сессию. В тексте указаны надёжные источники, ожидания по дереву файлов (`course.yml`, `module.yml`, `lesson.md`, tasks/checkpoints) и отсылка к `docs/course_authoring/COURSE_PACK_CONTRACT.md`.

4. **Генерация pack вне LMS**  
   Результат — набор файлов course pack по контракту. На этом шаге personal-lms только ждёт внешнее решение оператора.

5. **Промпт для Codex/Cursor**  
   Второй детерминированный промпт содержит роль Codex/Cursor, запреты на перегенерацию контента «с нуля» и на переписывание runtime-архитектуры; шаги: встройка дерева контента, `validate_content`, правки контрактно-совместимых ошибок, `pytest`, ручное открытие PR.

6. **Валидация и принятие**  
   После merge курса в репозиторий администратор выставляет заявке статус `implemented`.

## Справочная документация в репозитории

- [COURSE_PACK_CONTRACT.md](COURSE_PACK_CONTRACT.md) — машинный и авторский контракт pack.
- [CHATGPT_COURSE_GENERATION_PROMPT.md](CHATGPT_COURSE_GENERATION_PROMPT.md) — ручной канонический шаблон промпта; дублируется server-side сборкой для копирования из LMS.
- [CODEX_COURSE_IMPORT_PROMPT.md](CODEX_COURSE_IMPORT_PROMPT.md) — ручной шаблон промпта для Codex/Cursor; см. также админ-детали заявки.

## Статусы заявки

| Статус | Смысл |
|--------|--------|
| submitted | Отправлена учеником |
| reviewing | Изучает администратор |
| accepted | Одобрено к внешней работе над pack |
| rejected | Отказ с пояснением в admin notes |
| implemented | Pack доставлен в каталог; workflow завершён |

Переходы из терминальных `rejected` и `implemented` в другие статусы в коде запрещены, чтобы сохранять однозначный audit trail.
